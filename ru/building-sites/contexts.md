Контекст — именованный набор переопределений конфигурации. Запрос выполняется в этом наборе. У него свои настройки, своя ветка дерева ресурсов и свои правила доступа.

В поставке MODX два контекста: `web` (Website) для фронтенда и `mgr` (Manager) для менеджера. **Ключ** — значение, которое передаётся в `initialize()` и `switchContext()`. **Имя** — подпись в интерфейсе.

## Создание контекста

Откройте **Админ** (шестерёнка в верхнем меню) → **Контексты**. Кнопка **Создать** открывает форму с четырьмя полями:

| Поле | Обязательное | Значение |
| --- | --- | --- |
| **Ключ контекста** | да | идентификатор контекста |
| **Название** | да | подпись в менеджере и в дереве ресурсов |
| **Описание** | нет | свободный текст |
| **Сортировка** | нет | порядок контекста в дереве |

Ключи `mgr`, `web` и `root` зарезервированы. Ключ начинается с буквы. Дальше допустимы буквы, цифры, дефис, точка и слэш. Подчёркивание отклоняется, поэтому `domain_2` не сохранится.

Новый контекст сразу получает доступ:

- группа пользователей **Administrator** получает политику *Context*
- анонимный пользователь получает политику *Load Only*: право `load` и больше ничего

Запись анонима видна как **(аноним)** на вкладке **Права доступа** этого контекста. Удалите её там, чтобы снять этот доступ.

Каждый контекст — отдельная ветка в дереве ресурсов. Перетащите ресурс, чтобы перенести его в другой контекст.

**Копировать** копирует настройки, правила доступа и источники медиа. В этом окне включён флажок **Копировать ресурсы**, и вместе с ним копируются ресурсы. Снимите флажок, чтобы ресурсы остались на месте.

## Настройки контекста

Настройка контекста переопределяет [системную настройку](building-sites/settings) с тем же именем. Настройка группы пользователей переопределяет настройку контекста. Настройка пользователя переопределяет настройку группы.

```
Системная настройка → Настройка контекста → Настройка группы пользователей → Настройка пользователя
```

Правьте настройку на вкладке **Настройки контекста**: **Контексты** → правый клик по контексту → **Редактировать**. Смена настройки сбрасывает кэш этого контекста. Очищать кэш вручную не нужно.

Настройки, которые контекст обычно переопределяет:

| Настройка | Что меняет |
| --- | --- |
| `base_url` | путь в адресе контекста |
| `http_host` | хост, под который собираются URL |
| `site_url` | полный адрес контекста: схема, хост и путь |
| `site_start` | ресурс, который открывается в контексте |
| `cultureKey`, `locale` | язык и локаль запроса |

Эти настройки задают cookie сессии у контекста. Значения ядра сохраняются, если контекст их не переопределяет:

| Настройка | Значение по умолчанию |
| --- | --- |
| `session_name` | пусто: PHP оставляет своё значение |
| `session_cookie_path` | `MODX_BASE_URL` или настройка `base_url`, если она задана |
| `session_cookie_domain` | пусто |
| `session_cookie_secure` | `false` |
| `session_cookie_httponly` | `true` |
| `session_cookie_samesite` | пусто |
| `session_cookie_lifetime` | `604800` (7 суток). Контекст может записать `0`, и тогда cookie живёт до закрытия браузера |

## Доступ к контексту

Доступ выдаётся группе пользователей. Откройте иконку замка в меню пользователя → **Контроль доступа** → группа пользователей → **Права доступа** → **Контексты**.

В панели доступа у группы пользователей пять вкладок: **Контексты**, **Группы ресурсов**, **Категории элементов**, **Источники файлов** и **Пространства имён**. Политика вкладку не выбирает. Шаблон политики должен относиться к той же группе, что и вкладка.

## Чтение настроек контекста

Настройку текущего контекста читают как любую другую. Вызов не показывает, с какого уровня взято значение:

``` php
[[++my_context_setting]]
```

``` php
$setting = $modx->getOption('my_context_setting');
```

Для конкретного контекста:

``` php
$setting = $modx->context->getOption('my_context_setting');
$setting = $modx->getContext('web')->getOption('my_context_setting');
```

Язык запроса берётся из первого источника, где есть значение:

1. параметр `cultureKey` запроса
2. `cultureKey` сессии
3. настройка пользователя `cultureKey`
4. `cultureKey` контекста
5. системная настройка `cultureKey`

Если все источники пустые или значение не проходит проверку символов, язык равен `en`. Допустимы `A-Z`, `a-z`, `0-9`, `_` и `-`. В менеджере после этого берётся `manager_language`.

## Выбор контекста во время запроса

Запрос начинается в контексте, который выбирает шлюз. Сменить контекст могут два механизма:

- файл шлюза `config.context.php` рядом с `index.php`. Файл возвращает ключ контекста, в котором начинается запрос. См. [Использование виртуальных хостов](building-sites/contexts/virtual-host);
- плагин на событие `OnHandleRequest`, который вызывает `switchContext()`. См. [Плагин шлюза](building-sites/contexts/gateway-plugin).

``` php
if ($modx->switchContext('domain2')) {
    // запрос продолжается в контексте "domain2"
}
```

`switchContext($contextKey, $reload = false)` возвращает `false`, когда контекст не загрузился и когда ключ уже текущий. Во втором случае контекст заново не загружается. Проверяйте результат: на запросе, который уже в `domain2`, пример выше уходит в ветку неудачи.

Переключение контекста во время запроса не подгружает свой обработчик сессии и не меняет язык, локаль и cookie сессии. Они берутся из контекста, с которого стартовал `index.php`. Домену со своим языком или cookie нужен свой каталог с `config.context.php`. См. [Использование виртуальных хостов](building-sites/contexts/virtual-host).

## События

| Событие | Когда вызывается |
| --- | --- |
| `OnContextInit` | контекст загружен. Успешный `switchContext()` в другой контекст его загружает. Вызов для уже текущего контекста не загружает |
| `OnContextBeforeSave` | перед сохранением контекста |
| `OnContextSave` | после сохранения контекста |
| `OnContextBeforeRemove` | перед удалением контекста |
| `OnContextRemove` | после удаления контекста |
| `OnContextFormPrerender` | до отрисовки формы контекста |
| `OnContextFormRender` | после отрисовки формы контекста |

События MODX 2, которые часто называют в старых материалах, в MODX 3 не существуют: `OnContextSwitch`, `OnSiteInit`, `OnSiteRender`, `OnManagerInit` и `OnBeforeRequest`.

## Системные настройки

| Настройка | Значение по умолчанию | Что делает |
| --- | --- | --- |
| `default_context` | `web` | контекст в форме создания, если ресурс создаётся не внутри ветки другого контекста. Ветка дерева задаёт свой контекст |
| `access_context_enabled` | `true` | проверяет доступ к контексту на каждом запросе. Отключение игнорирует все правила доступа к контекстам |
| `allow_forward_across_contexts` | `false` | разрешает символьной ссылке и `sendForward()` доходить до ресурса в другом контексте |
| `cache_context_settings` | `true` | кэширует настройки контекстов |
| `use_context_resource_table` | `true` | ведёт таблицу ресурсов, принадлежащих нескольким контекстам |
| `context_tree_sort` | `true` | включает сортировку контекстов в дереве ресурсов. Поле задаёт `context_tree_sortby` |
| `context_tree_sortby` | `rank` | поле, по которому сортируются контексты дерева |
| `context_tree_sortdir` | `ASC` | направление сортировки |

## Источники медиа контекста

Источник медиа элемента можно задать для одного контекста. Элемент берёт источник своего контекста. Если у контекста источника нет, элемент сохраняет свой источник по умолчанию.

## Один ресурс в нескольких контекстах

Обычно ресурс принадлежит одному контексту. Когда включена настройка `use_context_resource_table`, таблица `context_resource` хранит ресурсы, принадлежащие нескольким контекстам. Такой ресурс находится в каждом из указанных контекстов.
