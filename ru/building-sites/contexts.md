Контекст — это именованный набор переопределений конфигурации, в котором выполняется запрос: свои настройки, своя ветка дерева ресурсов и свои правила доступа.

В MODX поставляется два контекста — `web` (Website) для фронтенда и `mgr` (Manager) для менеджера. Контекст адресуется **ключом** — значением, которое передаётся в `initialize()` и `switchContext()`. **Имя** — только подпись в интерфейсе.

## Создание контекста

Контексты управляются в менеджере: **Admin** (шестерёнка в верхнем меню) → **Contexts** (`?a=context`). Кнопка **Create** открывает форму с четырьмя полями:

| Поле | Обязательное | Значение |
| --- | --- | --- |
| `key` | да | идентификатор контекста |
| `name` | да | подпись, которая показывается в менеджере и в дереве ресурсов |
| `description` | нет | свободный текст |
| `rank` | нет | порядок контекста в дереве |

Ключи `mgr`, `web` и `root` зарезервированы ядром.

Новый контекст сразу получает доступ: группа пользователей **Administrator** — политику *Context*, анонимный пользователь — политику *Load Only*, то есть право `load` и больше ничего. Запись анонимного пользователя видна как **(anonymous)** на вкладке **Access Permissions** контекста, и её удаление там снимает этот доступ.

Контексты появляются в дереве ресурсов отдельной веткой. Ресурсы переносятся между контекстами перетаскиванием.

## Настройки контекста

Настройки контекста переопределяют [системные настройки](building-sites/settings) с тем же именем, а настройки пользователя — настройки контекста. Порядок такой:

```
Системная настройка → Настройка контекста → Настройка пользователя
```

Настройка контекста правится на вкладке **Context Settings**: **Contexts** → правый клик по контексту → **Edit**. Смена настройки сбрасывает кэш этого контекста, поэтому очищать кэш вручную не нужно.

Настройки, которые контекст обычно переопределяет:

| Настройка | Что меняет |
| --- | --- |
| `base_url` | часть пути в URL контекста |
| `http_host` | хост, под который собираются URL |
| `site_url` | полный URL контекста: схема, хост и путь |
| `site_start` | ресурс, который открывается в контексте |
| `cultureKey`, `locale` | язык и локаль запроса |

Настройки сессии настраивают cookie сессии контекста и сохраняют значения ядра, если контекст их не переопределяет:

| Настройка | Значение по умолчанию |
| --- | --- |
| `session_name` | пусто — PHP оставляет своё значение |
| `session_cookie_path` | `MODX_BASE_URL` или настройка `base_url`, если она задана |
| `session_cookie_domain` | пусто |
| `session_cookie_secure` | `false` |
| `session_cookie_httponly` | `true` |
| `session_cookie_samesite` | пусто |
| `session_cookie_lifetime` | `0` |

## Доступ к контексту

Доступ к контексту выдаётся группам пользователей на вкладке **Contexts** панели доступа: иконка замка в меню пользователя → **Access Control Lists** → группа пользователей → **Access Permissions** → **Contexts**.

Политика на контексте определяет, какая из пяти областей доступа действует: Context, Resource Group, Element Category, Media Source и Namespace. Политика без области покрывает сам контекст.

## Чтение настроек контекста

Настройку текущего контекста читают как любую другую настройку — уровень, с которого она пришла, читателю не виден:

``` php
[[++my_context_setting]]
```

``` php
$setting = $modx->getOption('my_context_setting');
```

Настройку конкретного контекста читают у этого контекста:

``` php
$setting = $modx->context->getOption('my_context_setting');
$setting = $modx->getContext('web')->getOption('my_context_setting');
```

Язык запроса берётся из первого источника, где есть значение:

1. параметр `cultureKey` запроса
2. `cultureKey` сессии
3. `cultureKey` контекста
4. системная настройка `cultureKey`

Код допускает в `cultureKey` только символы `A-Z`, `a-z`, `0-9`, `_` и `-`.

## Выбор контекста во время запроса

Запрос начинается в контексте, который называет гейтвей. Сменить контекст могут два механизма:

- файл гейтвея `config.context.php` рядом с `index.php` — файл возвращает ключ контекста, в котором начинается запрос. См. [Использование виртуальных хостов](building-sites/contexts/virtual-host);
- плагин на событие `OnHandleRequest`, который вызывает `switchContext()`. См. [Плагин шлюза](building-sites/contexts/gateway-plugin).

Метод, который переключает контекст:

``` php
if ($modx->switchContext('domain2')) {
    // запрос продолжается в контексте "domain2"
}
```

`switchContext($contextKey, $reload = false)` возвращает `false`, когда контекст не загрузился, поэтому результат стоит проверять.

Переключение контекста **не** подгружает свой session handler — его задаёт гейтвей: см. [Плагин шлюза](building-sites/contexts/gateway-plugin).

## События

| Событие | Когда вызывается |
| --- | --- |
| `OnContextInit` | контекст загружен: на каждом запросе и при каждом `switchContext()` |
| `OnContextBeforeSave` | перед сохранением контекста |
| `OnContextSave` | после сохранения контекста |
| `OnContextUpdate` | контекст обновлён в менеджере |
| `OnContextBeforeRemove` | перед удалением контекста |
| `OnContextRemove` | после удаления контекста |
| `OnContextFormPrerender` | до отрисовки формы контекста |
| `OnContextFormRender` | после отрисовки формы контекста |

События MODX 2, которые часто встречаются в старых материалах — `OnContextSwitch`, `OnSiteInit`, `OnSiteRender`, `OnManagerInit` и `OnBeforeRequest` — в MODX 3 не существуют.

## Системные настройки

| Настройка | Значение по умолчанию | Что делает |
| --- | --- | --- |
| `default_context` | `web` | контекст, в котором создаются новые ресурсы |
| `access_context_enabled` | `true` | проверяет доступ к контексту на каждом запросе; отключение игнорирует все правила доступа к контекстам |
| `allow_forward_across_contexts` | `false` | разрешает символьной ссылке и `sendForward()` доходить до ресурса в другом контексте |
| `cache_context_settings` | `true` | кэширует настройки контекстов |
| `use_context_resource_table` | `true` | ведёт таблицу ресурсов, принадлежащих нескольким контекстам |
| `context_tree_sort` | `true` | сортирует контексты в дереве ресурсов по названию |
| `context_tree_sortby` | `rank` | поле, по которому сортируются контексты дерева |
| `context_tree_sortdir` | `ASC` | направление сортировки |

## Процессоры

Процессоры контекстов и требуемое право для каждого из них:

| Процессор | Право |
| --- | --- |
| `Context/Create` | `new_context` |
| `Context/Duplicate` | `new_context` |
| `Context/Get` | `view_context` |
| `Context/GetList` | `view_context` |
| `Context/Update` | `edit_context` |
| `Context/UpdateFromGrid` | `edit_context` |
| `Context/Remove` | `delete_context` |
| `Context/Setting/Create` | `settings` |
| `Context/Setting/Get` | `settings` |
| `Context/Setting/GetList` | `settings` |
| `Context/Setting/Remove` | `settings` |
| `Context/Setting/Update` | политика `save` контекста |

`Context/Duplicate` копирует настройки, правила доступа и источники медиа контекста, а с `duplicateResources=1` — ещё и его ресурсы.

## Источники медиа контекста

Источник медиа элемента можно задать для отдельного контекста. Элемент берёт источник своего контекста и сохраняет источник элемента по умолчанию, если у контекста источника нет.

## Один ресурс в нескольких контекстах

Обычно ресурс принадлежит одному контексту. Когда включена настройка `use_context_resource_table`, таблица `context_resource` хранит ресурсы, принадлежащие нескольким контекстам, и такой ресурс находится в каждом из указанных.
