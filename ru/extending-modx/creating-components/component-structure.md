Все приличные дополнения к MODX распространяются транспортными пакетами: это zip-файлы с определённой структурой.

При установке они могут выполнять разные действия: создавать таблицы, менять системные настройки, копировать файлы и т.д.

Писать транспортный пакет с нуля долго, муторно и чревато ошибками. Лучше взять проверенную заготовку **modExtra**: почти все мои дополнения написаны с её помощью.

Поэтому сегодня нужно скачать [modExtra из репозитория](https://github.com/bezumkin/modExtra) и разобрать структуру будущего компонента: зачем там столько файлов и каталогов?

Конечно, разберём и сборщик пакета: как он работает и как настраивается.

## Загружаем modExtra

Заготовка лежит в репозитории на GitHub, поэтому проще всего клонировать её к себе на компьютер.
Есть как минимум 2 способа:

- Если вы не знакомы с Git или он ещё не установлен, просто скачайте и распакуйте [архив с файлами](https://github.com/bezumkin/modExtra/archive/master.zip)
- Если Git уже установлен, клонируем репозиторий:

``` php
git clone https://github.com/bezumkin/modExtra.git
```

и удаляем из него каталог `./modExtra/.git`. Он нам не нужен.
Теперь нужно перенести файлы и каталоги в наш проект. Он лежит у вас на компьютере (в прошлом уроке мы указали путь к нему), поэтому файлы можно просто скопировать через проводник. PhpStorm увидит и проиндексирует изменения.

Должно получиться так:

![](/2.x/ru/extending-modx/creating-components/component-structure/structure-1.png)

`test.php` можно смело удалить.

## Структура компонента

Обычный пакет состоит из 3 каталогов:

- `_build`: скрипты сборки компонента в транспортный пакет
- `assets`: файлы, которые должны быть доступны снаружи
- `core`: файлы внутренней логики компонента
- `README.md`: файл с общим описанием компонента, нужен для будущего репозитория на GitHub
- `rename_it.php`: новый скрипт переименования заготовки на PHP
- `rename_it.sh`: старый скрипт переименования на Perl

### Каталог core

Самый важный каталог компонента: здесь вся логика его работы.

Этот каталог нужно копировать на рабочий сайт, поэтому он выглядит так:

``` plain
- core
-- components
--- component_name
---- everything is necessary here
```

То есть структура каталогов устроена так, чтобы скопироваться в нужное место `/core` сайта.

#### Основные каталоги

- **controllers**: файлы подготовки страниц админки. Загружают нужные скрипты и стили.
- **docs**: история изменений, инструкция и лицензия. Эти файлы участвуют в описании пакета.
- **elements**: устанавливаемые чанки, сниппеты и другие возможные наследники `modElement`
- **lexicon**: словари компонента, обычно только en и ru
- **model**: каталог с объектами компонента и моделями таблиц БД, обычно только для MySQL. Здесь же лежит основной рабочий класс компонента.
- **processors**: файлы, которые выполняют одну небольшую функцию. Как правило, обрабатывают запросы из админки.
Обратите внимание: к файлам в этом каталоге нельзя обратиться снаружи. То есть здесь нельзя хранить скрипты, к которым вы хотите обратиться из браузера.

Это файлы ядра. В MODX каталог core можно вынести за пределы сайта или даже использовать один core для нескольких установок.

Если нужно открыть что-то из браузера, для этого есть assets.

### Каталог assets

Каталог, доступный из браузера для запросов. Здесь хранятся файлы `*.js, *.css and php-connectors` для запросов админки.

По умолчанию коннектор один: именно к нему обращаются страницы админки, чтобы выполнить задачи.
Здесь особо рассказывать нечего, всё и так понятно.

### Каталог _build

Пожалуй, самая интересная часть modExtra. В отличие от стандартных скриптов сборки MODX, в modExtra всё очень гибко.

### Конфигурация

Это служебный каталог. Его не будет в конечном пакете, потому что именно его скрипты собирают пакет.

- **data**: список сниппетов, чанков и других `modElements` для установки
- **includes**: вспомогательные функции для работы сборщика
- **properties**: список свойств сниппетов. Базовое имя файла должно совпадать с именем сниппета.
- **resolvers**: вспомогательные скрипты, которые выполняются на конечном сайте при установке пакета

В корне сборщика лежат особые файлы.

Файл сборки: `build.transport.php`. Он подключает конфиг `build.config.php`, в котором хранятся настройки:

- Имя компонента
- Версия
- Нужно ли сразу устанавливать компонент при сборке?
- Определение рабочих каталогов
- Настройка устанавливаемых объектов

Про объекты нужно рассказать подробнее. В MODX Revolution почти всё является объектом: и чанки, и сниппеты, и шаблоны.
У объектов есть разные свойства для работы в MODX. Но при установке пакета нас интересуют не свойства этих объектов, а то, как их устанавливать и обновлять.

Поэтому транспортный пакет по сути другой специальный объект `modTransportVehicle`, и у него есть свойства, которые описывают, как установить все чанки, сниппеты и шаблоны пакета.

По идее, в скрипте установки (`build.transport.php`) нужно задать поведение всех устанавливаемых объектов:

- Категория, к которой относится объект
- Его первичный ключ, чтобы определять дубликаты?
- Что делать, если такой ключ уже есть: перезаписывать или нет? (обновлять чанки и сниппеты?)
- Свойства дочерних объектов (если есть)

Всё это выглядит довольно сложно, и на деле так и есть.

Поэтому я переписал скрипты установки так, чтобы все основные настройки были в `build.config.php`, и алгоритм теперь такой:

1. В `build.transport.php` залезать вообще не нужно
2. Нужно ли упаковывать объект, задаётся объявлением константы `BUILD_name_of_object_UPDATE`
3. Обновление объекта задаётся в `BUILD_name_of_object_UPDATE`
4. Статичность объекта задаётся в `BUILD_name_of_object_STATIC`
5. Скрипты, которые выполнятся при установке пакета (resolvers), указываются в массиве `$BUILD_RESOLVERS`

Таким образом, всю работу по настройке пакета и добавлению или удалению можно разбить на 4 этапа:

1. Добавляем нужные объекты в `_build` в `/data/transport.objecttype.php` (об этом чуть ниже)
2. Указываем, как их устанавливать, в конфиге
3. Добавляем resolver в `_build/resolvers/resolve.anyname.php`
4. Указываем имя resolver в конфиге

Очевидно, что при такой структуре сборщика нам будет очень просто включать (или исключать) разные объекты в пакет.

### Устанавливаемые объекты

Собственно, это наши чанки, сниппеты и т.д.

Файлы с объектами у меня состоят из массива и цикла, который разбирает этот массив и возвращает уже готовые объекты.
Логика простая: уникальные значения объекта лежат в массиве, а значения по умолчанию добавляются в цикле плюс настройки статичности элементов из конфига.

Вот стандартный массив с одним чанком для **modExtra**:

``` php
$tmp = array(
    'tpl.modExtra.item' => array(
        'file' => 'item',   // File name in /core/components/имя/chunks/
        'description' => '',    // Description - will be visible in the corresponding field in the admin panel
    ),
);
```

Другие объекты добавляются похожим образом.

Если вы хоть немного знакомы с PHP, вопросов не будет: просто посмотрите исходники.

Всем элементам MODX можно задать параметры. Они будут видны на соответствующей вкладке при просмотре элемента.

![](/2.x/ru/extending-modx/creating-components/component-structure/structure-2.png)

Правило хорошего тона: всегда прописывайте параметры сниппетам. Для остальных они особо не нужны.

Скрипт сборки ищет параметры для сниппетов в каталоге `_build/properties/`. Файлы там устроены по тому же принципу: массив с уникальными значениями и цикл со значениями по умолчанию.

### Вспомогательные скрипты (resolvers)

Это специальные файлы, которые выполняются при разных действиях с пакетом: установке, обновлении и удалении.

Файлы resolver лежат в `_build/resolvers/` и выглядят примерно так:

``` php
if ($object->xpdo) {
    /* @var modX $modx */
    $modx =& $object->xpdo;

    switch ($options[xPDOTransport::PACKAGE_ACTION]) {
        case xPDOTransport::ACTION_INSTALL:
            // Actions on first package installation
            break;

        case xPDOTransport::ACTION_UPGRADE:
            // Actions when updating a package
            break;

        case xPDOTransport::ACTION_UNINSTALL:
            // What to do when removing a package
            break;
    }
}
return true;
```

Здесь можно делать с системой, на которую ставится пакет, что угодно, хоть удалить весь сайт: вам доступен класс modX.
Напоминаю: активные resolvers для сборки указываются в `$BUILD_RESOLVERS`.

## Заключение

Возможно, что-то в работе сборщика покажется непонятным, но мы ещё разберёмся с ним, когда будем упаковывать готовый код.

Главное помните: есть универсальный набор скриптов, который соберёт всё нужное в транспортный пакет.

В следующем уроке мы выгрузим **modExtra** на сервер, переименуем в **Sendex**, немного изменим, соберём в пакет и установим.
